# ldm-memory-system：认知资产统一治理

> 定位：交接skill让你的AI不失忆，本skill让它不失智。
> 哲学：Memory是指针，不是数据库；治理是统一的，不分类目。

## 一、统一治理四问（外壳）

所有类目——Memory条目、文档、Skill、指针——过同一套四问：

```
① 住哪层？   该在 Skill / 文档 / Memory 哪层？住错层 → 降级或上收
② 真源在哪？ 唯一真源是哪个文件？副本失效 → 删副本；真源失效 → 修真源
③ 还准吗？   指向的东西还在吗？计数对吗？项目还活着吗？→ 当场验证
④ 有索引吗？ 所在目录有README吗？长文档有##章节吗？skill有description吗？
             没有 → 黑数据，补索引
```

**为什么四问能统一？** 治理的本质就这四件事，不分类目。同一套问题，换个对象而已。

### 四问 × 类目矩阵

| 类目 | ①住哪层 | ②真源在哪 | ③还准吗 | ④有索引吗 |
|---|---|---|---|---|
| Memory条目 | 三选一 | 看内容类型 | fetch/stat当场验证 | 指针→指向有索引的文档 |
| 文档 | 文档层 | 自身或上级文档 | 版本号检查 | 目录README + ##章节 |
| Skill | Skill层 | 本地真源目录 | 流程/轮换表最新？ | frontmatter的description |
| 指针 | 各层 | 指向的目标文件 | 目标还存在吗 | 目标有索引吗 |

## 二、内核：三层架构 + SOT链 + B级分级（原创，重构不动）

### 三层架构（地图：知识放哪个仓库）

| 层 | 存什么 | 粒度 | 容量 |
|---|---|---|---|
| Skill（操作手册） | 可复用操作手册、教训集、完整流程 | 完整文档 | 无限 |
| 文档系统（项目资料库） | 项目详情、成稿、表格、选题库 | 按项目分文件夹 | 无限 |
| Memory（随身小本子） | 铁律、进度数字、路由指针 | 一行一条，§分隔 | ~2000字符 |

红线：对话原文→聊天记录存档；临时状态→会话搜索；完整key/完整路径→配置文件。都不许进Memory。

### SOT链（法律：每条知识只有一个真身）

**Skill > 本地md文档 > 聊天存档 > Memory**

1. 一条知识只能住一层（真源层），其他层最多留指针
2. 更新时改真源层，禁止平行开副本
3. 写入前先问：这知识最后会不会被纠正？会 → 放能被纠正的那层

### B级分级（包装：Memory条目写成什么样）

- **B级为标准格式**：结论 + 关键数字 + 推导逻辑概要
- 不存纯结论（缺推导，未来无法判断还适不适用）
- 不存完整表格（放项目目录，Memory只留一行指针）
- 进度数字A级即可（无歧义的纯数字）；铁律/指针/环境配置用B级

## 三、两阶段

### 阶段一【搭建】：从零建这套系统

适用：新用户第一次搭建；或系统混乱（无索引/无分类/不知道哪些该升级）。

先问3个问题（决定结构深度和毕业判断）：
1. 你有哪几个长期项目？（决定文档层怎么分文件夹）
2. 哪些文件最常被引用？（决定哪些要建索引）
3. 哪些操作反复做过3次以上？（决定哪些该毕业成skill）

然后按五步搭建（详见 references/setup-guide.md）：
1. 画三层结构图（用用户自己的项目举例）
2. 建文档层：按项目建文件夹 + 每目录一个README + 长文档##章节
3. 建Memory层：清点现有条目 → 四问归类 → B级格式重写 → 不存key/完整路径
4. 定毕业标准（见第四章）
5. 试跑验证：搭完跑一次维护扫描，确认结构能用

最小可行版：怕复杂的新用户，只搭 Memory 分类 + 根目录README，文档层和skill层用到再建。不强制一次搭完。

### 阶段二【维护】：日常/定期扫描

适用：用户说「清理memory」「memory体检」「跑一遍项目」；或新增memory条目时按写入铁律执行。

五步（详见 references/scan-workflow.md）：
1. 逐条判定：每条内容过四问
2. 验证指针：fetch/stat/cronjob list 当场验证
3. 三张清单：待删除候审单 / 待降级归档单 / 指针失效单
4. 用户拍板：说删才删，说留就留（硬卡点，不能跳）
5. 踩坑记录本：新坑写回本skill

## 四、毕业标准（什么时候文档→skill）

一个内容从文档层毕业成skill，必须同时满足4条：

```
① 重复性：同一流程出现过3次以上（不是一次性的）
② 换人能跑：别人/别的Agent拿到也能执行（不含只有你懂的隐含信息）
③ 有触发条件：能写清楚"什么时候该用它"（description可自动发现）
④ 用户确认：用户亲口说"这个以后常做"（Agent不能自己判断）
```

不满足 → 留在文档层，别急着做成skill。

## 五、执行边界

- 本skill是心法+检查清单，不内置自动化定时任务
- 所有维护动作由人发起或经人确认后才执行
- 定时任务如果读取文件，prompt必须加容错：文件不存在时输出提示然后正常结束，不报错崩掉
- 结项只认用户亲口说（「XX项目不做了/完结了」），Agent不得自行推断（离职≠项目结束、停更≠结项）
- 不处理：代码/部署/运行态一致性（neat-freak）、对话存档（ldm-session-handoff）、内容创作质量

## 六、踩坑记录本

### 6.0 严格按流程执行，不能跳步（2026-08-28血泪教训）

用户让我跑记忆断舍离skill，我犯了以下错误：

**错误1：直接删了10条memory，没有经过用户确认**
- 我自己判断哪些该删哪些该留，然后直接执行了
- 违反了核心规则："名单必须给用户过目；说删才删，说留就留"

**错误2：恢复后又自己判断，没有产出三张清单给用户拍板**

**错误3：验证指针时没有完整流程**（只验证部分token/路径，没验证cron ID、没检查key）

**错误4：没认真读skill就动手**（加载了但没按5步严格执行）

**错误5：犯错后又犯新错来修复旧错**（删→恢复→再删→恶性循环）

**根本原因**：没把流程当成必须严格执行的步骤，一直在"赶紧完成"而不是"做对每一步"，没意识到"用户拍板"是不可跳过的硬卡点。

**正确流程（必须严格执行）**：
1. 逐条判定：识别每个条目的类型（铁律类/进度类/指针类/环境类）
2. 验证指针：fetch确认飞书token存在、本地路径存在、cron ID存在、检查memory里是否有完整API key
3. 产出三张清单：待删除候审单/待降级归档单/指针失效单
4. 用户拍板后执行：用户说"去做吧"才执行，不能自己判断自己删
5. 写进踩坑记录本：本次扫描发现的新坑记录到此处

### 5.1 指针膨胀：压缩是白做工，只进不出
Memory 从 721 字符（8.26压缩后）涨回 1,518 字符（8.27）。压缩动作本身有效，但没有淘汰出口，新事实天天往里塞。
**教训**：压缩是治标，淘汰机制才是治本。每次压缩完必须把「该删的」当场删掉，而不是只压缩措辞。

### 5.2 多副本打架：同一条知识住两层
「重启提示语只核对状态、没指令不主动执行」同时存在于用户档案条和独立memory条目；「心理画报」同时存在于成品条目和项目条目。
**教训**：扫描时重复条目=删除候审的第一信号，不用等用户说。SOT链生效前先扫重。

### 5.3 环境信息混入 memory：key/路径不该进内存
智谱API的完整key、base_url、模型配置曾长期住在memory里——真源是 config.yaml，memory里放 key 意味着 key 一换（用户换新key）memory 条目立刻变僵尸。
**教训**：凭据、完整路径、版本号都是「环境事实」，真源在配置文件，memory只留「智谱备用provider，用/model切换」这种指针。

### 5.4 结项误判风险：离职≠项目结束（用户亲口纠正）
用户7月底离开开怀，但8.27仍在以执行人身份写开怀榜单。若当时按「离职=结项」清理开怀条目，就是误杀。
**教训**：Agent 永远比用户晚知道项目状态。结项只认用户亲口说，任何推断（离职/停更/不活跃）都只能进候审单，不能直接删。

### 5.5 进度数字双源冲突
「心理画报已完成6期」在memory里，但skill进度表只有1期成品完成+1期待生图。两个源对不上。
**教训**：进度数字必须只在进度真源层（skill表/产出日志）更新，memory里的进度数字是快照，扫描时以真源为准并回写。

### 5.6 索引断档：session_index.json停在7月8日（2026-08-27发现）
60天存档目录，索引只覆盖30天（到7-08），7-09之后30天全部无索引。
**教训**：每次写路由器文件时必须同步更新session_index.json。索引和存档是一体的，不是"存档完再补索引"——是"写存档的同时就写索引"。

### 5.7 根目录散落27个文件无导航（2026-08-27发现）
个人决策辅助系统根目录下有27个文件/目录，没有任何总索引，不知道先读哪个。
**教训**：根目录必须有README总索引，包含入口文件、项目目录、快速导航。新建文件后顺手更新README。

### 5.8 索引不是独立层，是每层自带的纪律（2026-08-28重构）
曾把"索引层"画成四层架构的独立一层，后来发现过度设计：索引的本质是每层的自我索引纪律（Memory条目本身是指针、文档目录有README、skill有description），不是额外一个文件。
**教训**：不创建独立索引层。每层自带索引纪律，减少维护负担。

### 5.9 只治理记忆=类目隔离（2026-08-28重构）
原skill只治理memory，不碰文档和skill，等于延续了"规则多副本打架"的病根（memory有断舍离、文档有README规则、skill有发布规则，三套规则互不看见）。
**教训**：治理必须统一所有类目（memory/文档/skill/指针），用同一套四问，否则等于没治理。
