# 阶段二：维护工作流

> 2026-08-27 首次实战验证，2026-08-28 重构为统一四问框架。
> 按此流程执行，产出三张清单给用户拍板。

## 适用场景

- 用户说「清理memory」「memory体检」「跑一遍项目」
- 系统用了一段时间，感觉乱了
- 新增memory条目时按写入铁律执行（第四步的子集）

## 前置准备

1. 加载 ldm-memory-system skill 作为裁判
2. 读取当前 memory 全部条目
3. 识别每个条目的类型：铁律类（永久）/ 进度类（定期核销）/ 指针类（指向外部）/ 环境类（配置/路径）

## 第一步：逐条判定（过四问）

对每条内容（memory条目/文档/skill/指针），过四问：

| 判定结果 | 动作 |
|---------|------|
| 该住当前层 | 保留 |
| 重复（与其他条目内容重叠）| 进待删除单 |
| 该住更低层（详情进skill/文档）| 进待降级单 |
| 涉及外部token/计数/路径 | 进指针验证单 |

四问检查：
```
① 住哪层？   该在 Skill / 文档 / Memory 哪层？住错层 → 降级或上收
② 真源在哪？ 唯一真源是哪个文件？副本失效 → 删副本；真源失效 → 修真源
③ 还准吗？   指向的东西还在吗？计数对吗？项目还活着吗？
④ 有索引吗？ 所在目录有README吗？长文档有##章节吗？skill有description吗？
```

## 第二步：验证指针（当场验证，不信缓存）

对所有涉及外部数据的指针，当场验证：

- 飞书token → fetch确认文档存在、计数正确
- 本地路径 → stat/ls确认文件存在、大小合理
- cron ID → cronjob list确认存在且状态正常
- API key → 确认真源在config.yaml，memory里没有完整key
- 版本号 → 检查是否有更新的版本取代它

## 第三步：产出三张清单

```markdown
① 待删除候审单（重复/僵尸）：
1. 「条目内容摘要」→ 与XX重复 / 已上收进skill

② 待降级归档单（该住低层）：
1. 「条目内容摘要」→ 真源在XX，memory只留指针

③ 指针失效单（已验证失效）：
1. 「条目内容摘要」→ 验证结果：失效/有效/待确认
```

## 第四步：用户拍板后执行

- 用户说"去做吧"= 确认（符合删除前列清单确认铁律）
- 用 memory tool 的 operations 批量执行
- 执行后报告：删除N条、降级N条、修正N条、memory从X%降到Y%

## 第五步：写进踩坑记录本

本次扫描发现的新坑 → 追加到 `references/pitfalls.md`（全量案例库，顺序编号）。SKILL.md 第六章的高频铁律区只收反复出现的教训，一般新坑只进 pitfalls.md。

## 注意事项

- 扫描时可能有并发更新（其他session同时改了memory），执行前重新读取
- 不要一次改太多条目，memory tool 是 all-or-nothing，一条匹配失败全部回滚
- 验证指针时用只读操作（fetch/stat/ls），不要修改任何外部数据
- 结项只认用户亲口说（「XX项目不做了/完结了」），Agent不得自行推断
- 删除/降级前必须给用户拍板，说删才删，说留就留
