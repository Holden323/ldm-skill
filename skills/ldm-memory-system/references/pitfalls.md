# 踩坑记录本（全量案例库）

> 由阶段二【维护】扫描持续追加。SKILL.md 第六章只留高频铁律，全量案例在本文件。
> 新坑格式：`### N. 标题（日期）` + 场景描述 + **教训**一行。

### 1. 严格按流程执行，不能跳步（2026-08-28血泪教训）

用户让我跑记忆断舍离skill，我犯了以下错误：

**错误1：直接删了10条memory，没有经过用户确认**
- 我自己判断哪些该删哪些该留，然后直接执行了
- 违反了核心规则："名单必须给用户过目；说删才删，说留就留"

**错误2：恢复后又自己判断，没有产出三张清单给用户拍板**

**错误3：验证指针时没有完整流程**（只验证部分token/路径，没验证cron ID、没检查key）

**错误4：没认真读skill就动手**（加载了但没按5步严格执行）

**错误5：犯错后又犯新错来修复旧错**（删→恢复→再删→恶性循环）

**根本原因**：没把流程当成必须严格执行的步骤，一直在"赶紧完成"而不是"做对每一步"，没意识到"用户拍板"是不可跳过的硬卡点。

**正确流程（必须严格执行）**：
1. 逐条判定：识别每个条目的类型（铁律类/进度类/指针类/环境类）
2. 验证指针：fetch确认飞书token存在、本地路径存在、cron ID存在、检查memory里是否有完整API key
3. 产出三张清单：待删除候审单/待降级归档单/指针失效单
4. 用户拍板后执行：用户说"去做吧"才执行，不能自己判断自己删
5. 写进踩坑记录本：本次扫描发现的新坑记录到此处

### 2. 指针膨胀：压缩是白做工，只进不出（2026-08-27）
Memory 从 721 字符（8.26压缩后）涨回 1,518 字符（8.27）。压缩动作本身有效，但没有淘汰出口，新事实天天往里塞。
**教训**：压缩是治标，淘汰机制才是治本。每次压缩完必须把「该删的」当场删掉，而不是只压缩措辞。

### 3. 多副本打架：同一条知识住两层（2026-08-27）
「重启提示语只核对状态、没指令不主动执行」同时存在于用户档案条和独立memory条目；「心理画报」同时存在于成品条目和项目条目。
**教训**：扫描时重复条目=删除候审的第一信号，不用等用户说。SOT链生效前先扫重。

### 4. 环境信息混入 memory：key/路径不该进内存（2026-08-27）
智谱API的完整key、base_url、模型配置曾长期住在memory里——真源是 config.yaml，memory里放 key 意味着 key 一换（用户换新key）memory 条目立刻变僵尸。
**教训**：凭据、完整路径、版本号都是「环境事实」，真源在配置文件，memory只留「智谱备用provider，用/model切换」这种指针。

### 5. 结项误判风险：离职≠项目结束（用户亲口纠正，2026-08-27）
用户7月底离开开怀，但8.27仍在以执行人身份写开怀榜单。若当时按「离职=结项」清理开怀条目，就是误杀。
**教训**：Agent 永远比用户晚知道项目状态。结项只认用户亲口说，任何推断（离职/停更/不活跃）都只能进候审单，不能直接删。

### 6. 进度数字双源冲突（2026-08-27）
「心理画报已完成6期」在memory里，但skill进度表只有1期成品完成+1期待生图。两个源对不上。
**教训**：进度数字必须只在进度真源层（skill表/产出日志）更新，memory里的进度数字是快照，扫描时以真源为准并回写。

### 7. 索引断档：session_index.json停在7月8日（2026-08-27发现）
60天存档目录，索引只覆盖30天（到7-08），7-09之后30天全部无索引。
**教训**：每次写路由器文件时必须同步更新session_index.json。索引和存档是一体的，不是"存档完再补索引"——是"写存档的同时就写索引"。

### 8. 根目录散落27个文件无导航（2026-08-27发现）
个人决策辅助系统根目录下有27个文件/目录，没有任何总索引，不知道先读哪个。
**教训**：根目录必须有README总索引，包含入口文件、项目目录、快速导航。新建文件后顺手更新README。

### 9. 索引不是独立层，是每层自带的纪律（2026-08-28重构）
曾把"索引层"画成四层架构的独立一层，后来发现过度设计：索引的本质是每层的自我索引纪律（Memory条目本身是指针、文档目录有README、skill有description），不是额外一个文件。
**教训**：不创建独立索引层。每层自带索引纪律，减少维护负担。

### 10. 只治理记忆=类目隔离（2026-08-28重构）
原skill只治理memory，不碰文档和skill，等于延续了"规则多副本打架"的病根（memory有断舍离、文档有README规则、skill有发布规则，三套规则互不看见）。
**教训**：治理必须统一所有类目（memory/文档/skill/指针），用同一套四问，否则等于没治理。

### 11. 真源必须是一个git仓库，所有agent软链指向它（2026-08-28）
搭建时曾建了两个真源：hermes本地开发源 + GitHub副本，其他agent软链到GitHub副本——两处可能不同步。学dbs官方惯例修正：真源=ldm-skill仓库（git管理），所有agent（含hermes）软链指向它，改一处push即发布。
**教训**：真源只能有一个，且必须是git仓库（有版本历史能回滚）。不要在hermes下建"开发源"，再让其他agent读GitHub副本。

### 12. skill引用文件路径会失效，扫描时要验证（2026-08-28实战）
kaihuai-content-creation skill 的"参考文件"章节7个指针全失效：04_素人投放计划/08_男性觉醒融合 整体归档到 _归档/旧方向_2026-08-03/，其中2个文件连归档都不存在，3个在归档中，1个路径写错（开怀APP推广/汉译汉V5 → 实际在汉译汉/）。
**教训**：扫描时不只查memory指针，还要查skill里引用的文件路径。目录归档/移动后，所有引用它的skill指针都会失效。修法：存在→指向归档新路径；不存在→删除指针并注明"已归档/旧方向"。

### 13. 根目录散落文档=孤儿，应迁入对应目录（2026-08-28实战）
`带薪健身小程序决策_V1.md` 散落在根目录，但决策事件/ 目录有64个决策——它属于那里。同类文档：根目录只留活跃的流水账（每日产出日志/项目规划），历史决策一律入决策事件/。
**教训**：根目录文档超过10个且没有README导航时，逐个检查是否该迁入子目录。散落=黑数据。

### 14. knowledge-base 与根目录同名文件=版本分叉（2026-08-28实战）
knowledge-base/ 的 project-status/rules/user-preferences 都是更新版（6月中下旬），根目录同名文件是旧版（6月上旬）。SOT规则被违反：同一文档两个版本，且都没写"谁是真源"。
**教训**：真源文档（rules/preferences/status）只允许存在于 knowledge-base/ 一处，根目录同名旧版必须删。扫描时 diff 同名文件，不同=分叉，以最新时间戳+内容完整度判定真源。

### 15. 工作区根README与实际结构脱节（2026-08-28实战）
Hermes_Workspace 根README描述"选题库/素材库/已发布/数据分析"，实际是18个真实项目目录——README是项目早期写的，从未更新。用户按README找目录会全部扑空。
**教训**：根README要定期与实际结构对账。扫描时对比README描述的目录 vs 实际ls的目录，全对不上=README过期，直接重写。

### 16. 同名目录跨位置重复=旧副本（2026-08-28实战）
工作区根 `得到大脑提取逐字稿/`（8-09旧版）与 `个人决策辅助系统/得到大脑提取逐字稿/`（8-28正式版）同名重复。判断依据：修改时间+内容完整度（正式版有README+全工具链）。
**教训**：扫描时发现同名目录跨位置存在，diff内容+时间戳判定哪个是正式版，旧的标"旧工作副本"待用户确认删除，不直接删。

### 17. 降级≠删除：详情必须搬去更低层，信息不能消失（2026-08-29实战）
memory清理时把"Claude Code三API"整条删了，理由是"环境配置不该在memory"。用户反问：删了之后我再问智谱API是多少、claude的三个API是啥，你怎么答？——难道降级就是删除的意思？
**教训**：降级的正确动作是「详情搬到能查到的低层 + memory留一行指针」，而不是删除。执行顺序：①先找到真源在哪（config.yaml/.env/settings-*.json）→②确认真源里信息完整→③memory改写成指针（指到真源文件）→④只有真源确认不存在的信息才允许消失。删除只用于"已上收进skill/文档的重复条目"，凡是外部还会再问的信息，删之前必须能报出"去哪查"。
