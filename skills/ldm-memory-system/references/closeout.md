# 收尾模式：项目或阶段做完后对齐知识

> 2026-11-10 新增。吸收 neat-freak（洁癖）的完成合同、反模式和两阶段汇报，按内容生产和多 Agent 协作的实际情况改写。项目、一集、一个阶段、一次交付做完后使用；用户说「收尾」「洁癖」「/neat」，或明显在做收尾时都走这里。

目标：做完一件事后，文档、规则、记忆和工作区都对齐到实际情况，下一次会话或第一次接手的人直接找到唯一现役答案。不是「多写一点」，而是「先减后加」。

## 范围

| 用户的说法 | 范围 |
|---|---|
| 「收个尾」「洁癖一下」，没指明对象 | 本次会话实际动过的项目，加上相关记忆条目 |
| 点名某个项目或某一集 | 该项目，加上相关记忆条目和它直接引用的共享工具说明 |
| 「整个工作区」「全部项目」 | 才逐项目扩大；先报规模和预计耗时 |

默认写入边界是范围内的项目和记忆。只读检查上级规则和同级项目名字，用来发现死引用；不改、不挪范围外的项目。别的窗口正在做的项目只读不碰。

## 完成合同：每个事实面都要有状态

| 事实面 | 要回答的问题 | 常见证据 |
|---|---|---|
| 项目实况 | 现在真正做到哪了？ | 项目自己的进度文件（流程核对表、从这里看、状态表）、成片和交付物、代码和测试 |
| 项目文档与入口 | 入口、说明、README 写的是不是现役答案？ | 入口文件、版本号、路径、交付说明 |
| 规则文件 | Agent 收到的约束是否同源、可执行、没有死引用？ | 层级 CLAUDE.md、AGENTS.md、钩子、共享工具说明 |
| 记忆 | 记忆里的状态、版本、路径还准吗？有没有进度流水账？ | 记忆索引、相关条目 |
| 工作区残留 | 有没有会话残留、中间文件、未提交改动？ | git status、临时脚本、测试帧、旧副本 |
| Git 与备份 | 该入库的入库了吗？有没有别人的暂存？ | git status、diff --cached、每日快照日志 |

每一面标成下面之一：

- `已核实`：查过，和实况一致，没改。
- `已改并核实`：改了，并且改完重新验证过。
- `待定`：无法当场验证，或要用户裁决。不能写进权威文档当事实。
- `不在范围`：这次不查，说明原因。
- `不适用`：项目没有这一面（比如没有 Git），如实写，不编证据。

不要把「git status 干净」「用户说过了」「自检通过」单独当成全部同步。

## 流程

1. **盘点。** 列出本次会话改过和产出的文件（git status、diff、会话里的写入）；读项目入口、实际生效的规则链和相关记忆条目；对项目目录和记忆目录各跑一次 `python3 scripts/scan.py <目录> --compact`，再看详情里的失效路径、断链、索引对账和「以 X 为准」声明。大项目不必通读全部文档，先读入口、规则和本次改动命中的文件。
2. **对齐事实。** 以项目实况为准，就地改写过期的入口、版本号、路径、状态句（「已上传」「未删」「大小」「下一步」也是指针）。找现有条目改，不追加平行版本。无法验证的标 `待定`。
3. **整理记忆。** 先减后加：删掉已完成的待办、进度流水、已被新版本取代的说法；状态改成绝对日期；进度留在项目文件，记忆只留红线、偏好和指针。只记录真实发生、以后可复用的教训，「本次没有新教训」是合法结果。
4. **查门禁。** 本次出现的错误如果在规则、记忆或踩坑记录里已是第三次，按主入口「同一个错犯到第三次就上门禁」处理。
5. **清点残留。** 一次性计划文档、调试脚本、`xxx_old`、`xxx_backup`、测试帧、临时预览。用户已有「可再生中间文件直接删」这类明确规则的，按规则处理并在汇报里列出；其余列删除候选，附理由。
6. **汇报，然后停下。** 按下面模板先完整汇报，保留现场。删除候选、提交、推送等着用户看完汇报后明确确认再做。用户在最初任务里说「做完后清理」，不替代这次汇报后的确认。
7. **清场（用户确认后）。** 只删确认过的项；删完重新核对一遍，补充汇报实际删了什么和剩下的警告。

## 先删的噪音（反模式）

| 反模式 | 处理 |
|---|---|
| 进度流水账写进记忆（「11-02 做了…11-03 又…」） | 进度回项目进度文件，记忆只留红线和指针 |
| 已完成的待办还挂着 | 核实后删除，或改写成仍有效的约束 |
| 单次事故长篇常驻记忆 | 提炼成一两句可复用的教训，过程留在复盘文档或 Git |
| 多个版本都自称现役 | 以项目实况裁决，旧版明确标历史或移进 历史版本/ |
| 「以过时副本为准」的声明 | 列为待用户拍板，改真源方向，旧副本顶部标历史档案 |
| 工具根本不读的配置或规则 | 连同引用它的规则一起删，真正意图改写成 Agent 能执行的文字 |
| 同一规则在全局、项目和 Skill 各抄一份 | 留一个真身，其他处放短指针 |
| 写着「保留作历史」却没人会看 | 有人会看的降级到项目文档；确实没人看的列删除候选 |

## 记忆面：各平台的加载上限

- Claude Code 自动记忆：索引 `~/.claude/projects/<项目>/memory/MEMORY.md` 会话启动时只加载前 200 行或 25 KB（先到者）；条目文件按需读。索引只放一行一条的指针，正文写在条目文件里。
- CLAUDE.md、AGENTS.md：全量加载，建议少于约 200 行；越长越难被遵守。这是质量预算，不是硬截断。
- Codex 等机器生成的记忆：通常不能手改，标 `只读`，只用产品给的入口提交更正。
- Hermes 等用记忆工具写的记忆：有字符预算，操作坑见 [pitfalls.md](pitfalls.md) 第 18 条。
- 没见过的平台：先找官方控制面，找不到就当只读。

## 汇报模板

```text
## 收尾完成（<范围>）

**影响**：<消除了哪些误导、风险或交接成本>

**事实面**
- 项目实况：<状态> — <证据>
- 项目文档与入口：<状态> — <改了什么>
- 规则文件：<状态>
- 记忆：<状态> — <删/改/新增几条>
- 工作区残留：<状态>
- Git 与备份：<状态>

**待你确认**
- 删除候选：<文件 + 理由>；未确认前一个都没删
- 无法裁决：<矛盾 + 两边证据>

**遗留**：<待定 / 不在范围 / 未消除的警告；没有就写「无」>
```

记忆索引超过平台上限的 70% 时才报读数。存在待清理现场时写明「现场保留，等你确认后清理」。

## 和 ldm-session-handoff 的配合

收尾管「知识和实况对齐」，交接管「会话原文、路由器和重启提示语」。用户两件都要时，先收尾再交接，交接的路由器引用收尾后的现役文件。
