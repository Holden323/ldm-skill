# 记忆断舍离

> 定位：交接skill让你的AI不失忆，本skill让它不失智。
> 哲学：Memory是指针，不是数据库。

## 一、三层架构（存哪一层）

| 层 | 存什么 | 粒度 |
|---|---|---|
| Agent内置记忆层（Hermes=memory tool / Claude=MEMORY.md / Codex=配置文件） | 路由指针、铁律、进度数字 | 一行一条 |
| Skills / 知识库 | 可复用操作手册、教训集 | 完整文档 |
| 文档系统 | 项目详情、成稿、表格 | 无限 |

红线：对话原文→聊天记录存档；临时状态→会话搜索；都不许进内置记忆。

## 二、信息分级（存成什么样）

- **B级为标准格式**：结论 + 关键数字 + 推导逻辑概要
- 不存纯结论（缺推导，未来无法判断还适不适用）
- 不存完整表格（放项目目录，内置记忆只留一行指针）

## 三、SOT链（唯一真源优先级）

**Skills > 本地md文档 > 聊天存档 > 内置记忆**

1. 一条知识只能住一层（真源层），其他层最多留指针
2. 更新时改真源层，禁止平行开副本
3. 写入前先问：这知识最后会不会被纠正？会 → 放能被纠正的那层

## 四、维护机制（何时淘汰）

### 4.1 结项信号（唯一合法来源）
- 只认用户亲口说的：「XX项目不做了/完结了」
- 听到后：①该项目条目转归档态【结项YYYY-MM-DD】②反问用户是否还有相关条目要一起标
- Agent不得自行推断结项（离职≠项目结束、停更≠结项）

### 4.2 僵尸候审（平时唯一维护动作）
- 机械扫描：30天未被读写的进度型条目 → 出候审名单
- 名单必须给用户过目；说删才删，说留就留

### 4.3 两段式回收
- 结项时：降级为一行压缩指针（项目名+终态数字）
- 真删除：等用户主动说「把XX清干净」

### 4.4 指针保鲜
- 涉及外部token/计数的指针：用之前fetch验证，不用信缓存值
- session开头收到重启提示语时，顺手核对指针有效性

## 五、索引规范

指针只指向"有索引的文档"，无索引的文档=黑数据。

### 5.1 对话索引
- 文件：对话存档目录下的索引文件（如 `session_index.json`）
- 格式：`{日期: [{id, title, source, router_file, has_record}]}`
- 规则：每次写路由器文件后，顺手更新索引文件当天条目
- 验证：目录数必须等于索引key数，定期扫描补缺

### 5.2 文档内部索引
- 每个长文档（>100行）必须有`## `章节标题（grep可检）
- 缺索引的文档 → 标记待补

### 5.3 根目录导航
- 根目录必须有README.md总索引
- 格式：入口文件→项目目录→工具→存档→快速导航
- 新建文件/目录后顺手更新README

## 六、踩坑记录本

### 6.0 严格按scan-workflow.md执行，不能跳步

用户让我跑记忆断舍离skill，我犯了以下错误：

**错误1：直接删了10条memory，没有经过用户确认**
- 我自己判断哪些该删哪些该留，然后直接执行了
- 违反了scan-workflow.md的核心规则："名单必须给用户过目；说删才删，说留就留"

**错误2：恢复后又自己判断，没有产出三张清单给用户拍板**
- 我把删掉的10条恢复回来，但又开始自己判断哪些该删
- 还是没按流程走，还是没给用户看三张清单

**错误3：验证指针时没有完整流程**
- 我只验证了部分飞书token和本地路径
- 没有验证cron ID、没有检查memory里是否有完整API key

**错误4：没认真读skill就动手**
- 我加载了memory-router skill，也读了scan-workflow.md
- 但没有严格按照5步执行，而是凭感觉操作

**错误5：犯错后又犯新错来修复旧错**
- 我删了10条→用户骂→我恢复→用户骂→我又自己判断→用户骂
- 形成了恶性循环，越修复越糟糕

**根本原因**：
1. 我没有把scan-workflow.md的5步当成必须严格执行的流程
2. 我一直在"赶紧完成"而不是"做对每一步"
3. 我没有意识到"用户拍板"是不可跳过的硬卡点

**正确流程（必须严格执行）**：
1. **逐条判定**：识别每个条目的类型（铁律类/进度类/指针类/环境类）
2. **验证指针**：fetch确认飞书token存在、本地路径存在、cron ID存在、检查memory里是否有完整API key
3. **产出三张清单**：待删除候审单/待降级归档单/指针失效单
4. **用户拍板后执行**：用户说"去做吧"才执行，不能自己判断自己删
5. **写进踩坑记录本**：本次扫描发现的新坑记录到此处

### 5.1 指针膨胀：压缩是白做工，只进不出
Memory 从 721 字符（8.26压缩后）涨回 1,518 字符（8.27）。压缩动作本身有效，但没有淘汰出口，新事实天天往里塞。
**教训**：压缩是治标，淘汰机制才是治本。每次压缩完必须把「该删的」当场删掉，而不是只压缩措辞。

### 5.2 多副本打架：同一条知识住两层
「重启提示语只核对状态、没指令不主动执行」同时存在于用户档案条和独立memory条目；「心理画报」同时存在于成品条目和项目条目。
**教训**：扫描时重复条目=删除候审的第一信号，不用等用户说。SOT链生效前先扫重。

### 5.3 环境信息混入 memory：key/路径不该进内存
智谱API的完整key、base_url、模型配置曾长期住在memory里——真源是配置文件，memory里放 key 意味着 key 一换（用户换新key）memory 条目立刻变僵尸。
**教训**：凭据、完整路径、版本号都是「环境事实」，真源在配置文件，memory只留「备用provider，用/model切换」这种指针。

### 5.4 结项误判风险：离职≠项目结束（用户亲口纠正）
用户7月底离开开怀，但8.27仍在以执行人身份写开怀榜单。若当时按「离职=结项」清理开怀条目，就是误杀。
**教训**：Agent 永远比用户晚知道项目状态。结项只认用户亲口说，任何推断（离职/停更/不活跃）都只能进候审单，不能直接删。

### 5.5 进度数字双源冲突
「心理画报已完成6期」在memory里，但skill进度表只有1期成品完成+1期待生图。两个源对不上。
**教训**：进度数字必须只在进度真源层（skill表/产出日志）更新，memory里的进度数字是快照，扫描时以真源为准并回写。

### 5.6 索引断档：对话索引停在7月8日（2026-08-27发现）
60天存档目录，索引只覆盖30天（到7-08），7-09之后30天全部无索引。
**教训**：每次写路由器文件时必须同步更新对话索引。索引和存档是一体的，不是"存档完再补索引"——是"写存档的同时就写索引"。

### 5.7 根目录散落27个文件无导航（2026-08-27发现）
项目根目录下有27个文件/目录，没有任何总索引，不知道先读哪个。
**教训**：根目录必须有README总索引，包含入口文件、项目目录、快速导航。新建文件后顺手更新README。

## 七、执行边界

- 本skill是心法+检查清单，不内置自动化定时任务
- 所有维护动作由人发起或经人确认后才执行
- 定时任务如果读取文件，prompt必须加容错：文件不存在时输出提示然后正常结束，不报错崩掉
